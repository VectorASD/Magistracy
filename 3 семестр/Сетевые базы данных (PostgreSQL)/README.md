# Usage

## Установка Docker Desktop (Windows)
Выполни в PowerShell с правами администратора:
```powershell
choco install docker-desktop -y
```

## Первый запуск (инициализация БД с безопасной передачей секретов)
Контейнер создаёт кластер, пользователя `admin` и базу `postgres`.  
Пароль и имя пользователя читаются из файлов в папке `./assets` (см. подготовку ниже).  
**Важно:** эта команда выполняется **один раз**, после чего том (value) `my-pgdata` будет содержать готовую базу.

```powershell
docker run --rm -it --name my-postgres `
  -v "${PWD}/assets:/run/secrets:ro" `
  -v my-pgdata:/var/lib/postgresql `
  -e POSTGRES_USER_FILE=/run/secrets/postgres-username `
  -e POSTGRES_PASSWORD_FILE=/run/secrets/postgres-passwd `
  -e POSTGRES_HOST_AUTH_METHOD=scram-sha-256 `
  -p 5432:5432 postgres:18.4
```

После появления строки `database system is ready to accept connections` нажми `Ctrl+C` – контейнер остановится и удалится (благодаря `--rm`), а том `my-pgdata` останется.

### Подготовка секретов (перед первым запуском)
В текущем каталоге, откуда запускается команда, уже должны быть файлы assets/postgres-username и assets/postgres-passwd, **БЕЗ!!!** переносов на новую строку (иначе затянет \r\n).
Или же можно изменить `${PWD}/assets` на своё.

## Последующие запуски (рабочий режим)
Контейнер стартует с уже готовыми данными, **без** секретов.  
Подключаться можно сразу.

```powershell
docker run --rm -d --name my-postgres `
  -v my-pgdata:/var/lib/postgresql `
  -p 5432:5432 postgres:18.4
```

## Подключение к PostgreSQL
### Внутри контейнера (через Unix-сокет, пароль не требуется)
```powershell
docker exec -it my-postgres psql -U admin -d postgres
```


# PostgreSQL выбор версий

## PostgreSQL 14 → 15

Ключевые изменения, важные для прикладных задач:
* **Поддержка SQL `MERGE`**. Это удобно: можно в одном запросе сделать «вставить, если нет, иначе обновить» без сложных конструкций. Раньше приходилось делать через `INSERT … ON CONFLICT`.
* **Сжатие Zstandard (zstd)**. В том числе на стороне сервера при `pg_basebackup`. Для бэкапов это часто даёт лучшую степень сжатия и скорость, чем gzip.
* **JSON-логи в структурированном виде**. Проще парсить логи из Python-скриптов (например, для мониторинга или ETL).
* **Улучшения производительности** при сортировке в памяти и на диске, а также при работе с агрегированными запросами и секционированными таблицами.

---

## PostgreSQL 15 → 16

Здесь много про репликацию и параллелизм:
* **Распараллеливание FULL и внутренних правых OUTER хэш-соединений**. Запросы с такими соединениями могут работать заметно быстрее.
* **Логическая репликация с резервных серверов**. Это сильно расширяет сценарии отказоустойчивости и выгрузки данных.
* **Параллельное выполнение больших транзакций подписчиками логической репликации**. Полезно, если вы делаете витрины, CDC-потоки или синхронизацию между базами.
* **Мониторинг I/O через `pg_stat_io`**. Удобно для профилирования нагрузки и поиска «узких мест» в скриптах.
* **Конструкторы и функции для SQL/JSON**. Работать с JSON-полями становится удобнее и выразительнее.

---

## PostgreSQL 16 → 17

Самые заметные новшества:
* **Новая система управления памятью для VACUUM**. Снижает пиковое потребление памяти и может ускорить сборку мусора в нагруженных базах.
* **Функция `JSON_TABLE()`**. Позволяет преобразовывать JSON прямо в табличное представление в SQL — очень удобно, когда данные приходят в JSON, а дальше нужна обычная реляционная обработка.
* **Потоковый ввод-вывод для последовательного чтения**. Улучшает пропускную способность при сканировании больших таблиц.
* **Ускорение поиска по нескольким значениям в B-tree индексе**. Полезно для запросов вида `WHERE id IN (...)` на больших списках.

---

## PostgreSQL 17 → 18

Пока это самая свежая ветка: в основном это **дальнейшие оптимизации, исправления и улучшения стабильности**, а также развитие уже добавленных фич (в т. ч. JSON, репликации, мониторинга). Конкретные «громкие» новинки обычно появляются в анонсах релизов, но на практике переход с 17 на 18 чаще всего даёт прирост за счёт оптимизаций планировщика и движка, а не за счёт новых синтаксических конструкций.

---

## Важные нюансы, которые стоит учитывать

* **Двоичная несовместимость мажорных версий.** Базу из одной мажорной версии нельзя просто «подключить» к другой: для обновления обычно используют `pg_upgrade`, дампы (`pg_dump`/`pg_restore`) или логическую репликацию.
* **Минорные версии (например, 16.1 → 16.5)** содержат в основном исправления ошибок и уязвимостей, они бинарно совместимы и обновляются проще.
* **Совместимость API и драйверов.** Для Python-кода (psycopg2, asyncpg и т. п.) переход между мажорными версиями почти никогда не ломает сам драйвер, но могут измениться SQL-синтаксис, поведение транзакций или параметры конфигурации.
